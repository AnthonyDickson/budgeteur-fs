# Architecture

The requirements the system is built around, how the server and client are
structured, and the rules that hold across both. Feature-level decisions live in
their design briefs ([balance sheet](balance-sheet.md),
[dashboard](dashboard.md)); storage, dates, and tests have their own docs.

## Requirements and constraints

- **Self-hosted.** The app runs on a home server behind a reverse proxy (nginx,
  Caddy). It is one deployable: the server serves the SPA, so there is no
  separate frontend host. See [deployment](deployment.md).
- **Any device.** A browser is the only client, so the same data is available
  from phone and desktop.
- **Several users, fully isolated.** Identity comes from an external OIDC
  provider; the app stores no credentials. Every row belongs to one user, and no
  request can read or change another user's data.
- **Exact money.** Amounts are exact to the cent, in one base currency. There is
  no multi-currency or FX support.
- **Bank data from CSV.** Transactions and balances are to be imported from CSV
  exports of New Zealand banks (ASB, Kiwibank) to reduce manual entry (roadmap).
- **No financial data left in the browser.** A shared browser must not expose
  one user's finances to the next, so the client never persists server data.
- **No server timezone.** The server needs no timezone configuration; the client
  supplies date ranges from its local calendar. See [dates](dates.md).

## Server

### Vertical slices

Each feature is a folder under `Feature/`, with one file per HTTP operation. A
slice's endpoint list is grouped by HTTP method and used by both the production
host and the test host, so a route is declared once. Routes follow
`/api/<resource>` for collections and `/api/<resource>/{id}` for items. IDs are
v7 UUIDs generated by the server; create requests carry no id. Every endpoint
carries OpenAPI metadata ([openapi](openapi.md)).

Dependencies are passed as function arguments. The database query context is
created once at startup and passed to each endpoint; there is no DI container.

### Dependency rules

`Domain/`, `Data/`, and `Shared/` form the shared kernel:

- **One-way dependencies: features → kernel.** The kernel never depends on a
  slice, and slices never import each other. `just lint` enforces both.
- **Ownership test.** Every type and rule has one owner. A concept belongs in
  the kernel only if more than one slice drives its changes, and it should
  change less often than its consumers. A kernel module that changes every
  sprint is mis-owned; move it into the slice that drives it.
- **Promote on the second consumer.** Code used by one slice stays in that
  slice, and moves to the kernel when a second slice needs it. This applies to
  DB mappings, refined types, and domain functions alike.
- **Invariants live with the type in `Domain/`; use-case rules stay in the
  slice.** Intrinsic validity (non-empty, length, rounding) is domain;
  orchestration (auth, queries, uniqueness) is feature.
- **Slices own their read shapes.** A feature needing a different shape (e.g. a
  dashboard aggregate) defines its own read model rather than growing the shared
  type.

### Domain types

Value invariants are enforced by **refined types**: a single-case union with a
private case, defined with the record that owns the field. The only way in is a
`create` function that validates and returns a `Result`; the only way out is
`value`. Consequences:

- **Records stay public.** A record with a refined field cannot be built with an
  invalid value, so the record itself needs no private constructor. Hiding it
  would also hide its fields from the DB mapping and the JSON encoder.
- **Unwrap at the edges only.** Refined values are unwrapped when mapping to a
  database row and when mapping to a response. Elsewhere they are opaque.
  Structural equality still holds, so tests compare them directly.
- **Stored rows are trusted.** Reading a row back into the domain does not
  re-validate; rows were validated on write.

### Representations at the boundary

A domain entity has up to three other representations, each kept separate:

| Representation | Shape                                 | Changes with     |
| -------------- | ------------------------------------- | ---------------- |
| Request DTO    | Raw primitives, validated by `create` | The API contract |
| Response DTO   | Primitives only, encode-only          | The API contract |
| Row            | Generated from the schema             | The schema       |

The row mapping (a slice's codec) and the response mapping are separate modules
because they have different dependencies and change for different reasons. DB
columns never reach the API. Because DTOs hold only primitives, JSON encoding
and OpenAPI schema generation need no custom code per type.

### Errors

Failures are values of one closed union, `DomainError`, and every handler
returns `Result<unit, DomainError>`. A single handler wrapper maps each case to
a status code (validation `400`, not found `404`, conflict `409`, missing user
claims `401`, everything else `500`) and every error response has the same JSON
body: error, details, status code, and request id. Platform exceptions (e.g.
from SQLite) are converted to `DomainError` in that wrapper, so slices never
handle them; a global middleware catches anything else as a last resort.

Integrity constraints are checked explicitly before writes, because SQLite does
not always report which column a violation came from. The checks are combined so
a client sees every failure in one `400` response. The `409` mapping remains as
a safety net for races between a check and its write. See
[database](database.md).

### Auth

Two authentication schemes sit behind a policy scheme that picks one per request
by the presence of an `Authorization: Bearer` header:

- **Cookie** — the SPA session, from the authorization code flow.
- **JWT bearer** — the API docs (Scalar), using PKCE. Development only.

Either satisfies the single `authenticated` policy that protects every API
endpoint. `/login` starts the challenge and redirects to the configured return
URL; `/logout` clears the session cookie. Outside development, cookies are
secure, `HttpOnly`, `SameSite=Lax`, with a one-hour sliding expiry.

Known limits:

- Claims come from the ID token; the userinfo endpoint is not called.
- Audience validation is off unless audiences are configured, because Authelia
  access tokens carry no `aud` claim.
- `/logout` clears only the local cookie. The provider session persists, as
  Authelia lacks RP-initiated logout.

Provider setup is in [prod-oidc-setup](prod-oidc-setup.md).

### Configuration

Settings are typed sections bound from `appsettings*.json` or environment
variables (e.g. `Oidc__ClientSecret`). Every section is validated at startup,
and the server refuses to boot, listing every missing or malformed setting,
rather than failing on first use.

### Logging

1. **Request-scoped logs.** Handlers append structured entries to a per-request
   log, emitted as one JSON array when the response completes, so entries for a
   request stay together instead of interleaving with concurrent requests.
2. **Global Serilog pipeline.** Startup and unhandled exceptions, as compact
   JSON on the console; file output is opt-in.

### Status endpoint

`GET /api/status` reports the build version, uptime, and database connectivity,
and returns `503` when the database is unreachable. Container health checks use
it, so it is unauthenticated.

## Client

### Shell and pages

Two layers of MVU. The shell owns routing, toasts, and session expiry; each
feature page owns its model, update, and view. The shell delegates to the active
page and lifts its effects. Pages return an `OutMsg` alongside model and effect
to ask the shell for shell-level behaviour (currently toasts), so the shell's
`update` is the one place child requests become shell effects.

| Condition                               | Pattern              |
| --------------------------------------- | -------------------- |
| Single feature, one concern             | Add to existing page |
| New feature with independent state      | New page module      |
| Feature shares state with existing page | Extend existing page |
| Global state (auth, theme, user prefs)  | Extend shell model   |

### Modals

Modals are state machines held in the page model, not stateful components. A
modal raises its own messages and returns its next state plus an optional write
request and outcome, which the page turns into effects and data changes. The
create/update and delete-confirmation machines are generic and shared; features
supply their own entities and forms.

Whether a dialog is open is derived from the model alone: a modal renders while
not hidden and renders nothing while hidden. A custom element opens the native
`<dialog>` when inserted and reports browser dismissals (Escape, outside click)
as a cancel. No effect opens or closes a dialog, so the screen cannot drift from
the model.

### Effect system

`update` returns a description of side effects as plain data, and one
interpreter executes them against the browser. Effects cover HTTP, localStorage,
navigation, document title, timers, message dispatch, and batching. Because
effects are values, unit tests assert on them without a browser or HTTP mocking.
The `Effect` type is the source of truth for the full list.

The shell rewrites HTTP effects so a `401` response triggers session expiry and
a redirect to login, instead of reaching the page.

### Routing

No router library. The shell intercepts internal link clicks and back/forward
navigation and delivers paths to `update`. Routes are declared in one module;
unknown paths render a 404 page.

### Server data

Pages fetch their data on every visit and show a loading state until it arrives.
Nothing from the server is cached in localStorage, which holds user preferences
only (e.g. the dashboard period). Cached data was removed because its keys were
not per user and survived logout.

### Same origin

The client always calls same-origin URLs. In development Vite proxies the
backend paths (`/api`, `/login`, `/logout`, `/signin-oidc`) to the server; in
production the server serves the SPA. No CORS is configured.

## Money

- The server rounds every amount to cents, midpoint away from zero, through the
  refined `Money` type. Code that rounds other amounts uses the same rule.
- Amounts are serialised as JSON strings, not numbers, so no JSON parser
  converts them to floating point.
- Arithmetic on money happens on the server in `decimal`. SQL aggregates are not
  used, because SQLite stores and sums money as doubles
  ([database](database.md#money-columns)). The client displays money and never
  computes with it, because JavaScript numbers are doubles; totals come from the
  API.

## Testing

Server tests run each slice's real endpoints against an in-memory database;
client tests call `update` and inspect the returned model and effects; E2E tests
run the full stack. What to test and where is decided by
[testing-strategy](testing-strategy.md).
