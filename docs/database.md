# Database

SQLite, with schema migrations applied by DbUp at startup and type-safe queries
generated by SqlHydra. SQLite fits the deployment: one self-hosted process, one
file to back up, no database server to run.

## Migrations

Migrations are numbered `.sql` files in `Data/Migrations/`, embedded in the
server assembly and applied once each, in order, at startup. Applied migrations
are recorded in a `SchemaVersions` table.

- **Never modify a released migration.** A migration is released once a version
  tag (created by the Docker Publish workflow) contains it; check with `git tag
  --contains <commit>`. Until then, edit it in place and run `just db-reset`.
  After release, schema changes go in a new file.
- **Migration paths are part of the schema history.** DbUp identifies a
  migration by its path. Moving or renaming an applied migration makes DbUp
  treat it as new and re-run it, which fails on an existing database.
- **Migrations run without the server.** A standalone script applies them, so a
  schema change can be migrated and the generated code refreshed while the
  domain code does not yet compile against it.

## Generated code

`Data/Db.fs` holds the row types and query context, generated by SqlHydra from a
migrated database. It is committed so a fresh clone builds without a database,
and it is never hand-edited. CI regenerates it from the migrations and fails if
the committed file differs.

Column types in migrations use SqlHydra's type hints (`GUID`, `BOOLEAN`, `DATE`,
`DATETIME`, `CURRENCY`, …). They are not real SQLite types; SQLite gives them a
type affinity and SqlHydra maps them to F# types. The first migration's header
documents the assumptions they carry: `GUID` columns hold v7 UUIDs, `DATETIME`
columns hold UTC instants, and `DATE` columns hold calendar dates
([dates](dates.md)).

Row types never reach the API. Each slice maps rows to and from its domain types
in a codec ([architecture](architecture.md#representations-at-the-boundary)).

## Integrity

- **Foreign keys** are a per-connection setting in SQLite, and builds without a
  default silently ignore them. The server enables them in the connection
  string, so every connection enforces them regardless of how SQLite was built.
- **WAL journal mode** is enabled at startup. It is stored in the database file,
  so it persists.
- **Constraints are checked before writes** so a violation returns a `400`
  naming the problem, rather than a `409` from the database
  ([architecture](architecture.md#errors)). The explicit checks mirror the
  schema's constraints and must be kept in step with it.

## Money columns

`CURRENCY` columns have NUMERIC affinity, so SQLite stores a decimal as a `REAL`
(an IEEE double) and it reads back rounded to 15 significant digits. Amounts up
to 15 significant digits (about $10 trillion in cents) round-trip exactly;
larger amounts drift. Aggregate money in F# on `decimal` after reading rows,
never with SQL `SUM`, which adds doubles.

## Connection string

The default, `Data Source=app.sqlite3`, is relative to the server project. In
production set `ConnectionStrings__Default` to an absolute path on persistent
storage ([deployment](deployment.md)).

## Workflows

- **After cloning:** nothing to generate. `just server-watch` creates the
  database and applies migrations.
- **Changing the schema:** `just db-migration name=<name>` scaffolds a file;
  write the SQL; `just db-update` applies it and regenerates `Db.fs`; fix the
  codecs that no longer compile; commit the migration and `Db.fs` together.
- **Starting fresh:** `just db-reset` deletes the database, re-applies every
  migration, and regenerates `Db.fs`. Use it after editing an unreleased
  migration or moving a migration file.
